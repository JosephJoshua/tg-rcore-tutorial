# 第八章实验报告：死锁检测

## 实现内容

### enable_deadlock_detect 系统调用（ID 469）
按进程切换死锁检测功能。`is_enable=1` 启用检测；`is_enable=0` 禁用。其他值返回 -1。

### 互斥锁死锁检测
使用**等待图环路检测**：
1. 当线程 T 请求由线程 T' 持有的互斥锁 M 时，沿链追踪：T' → T' 正在等待的互斥锁 → 该锁的持有者 → ...
2. 若链路回到 T，则检测到死锁 → 返回 `-0xDEAD`（-57005）
3. 若链路到达未等待的线程或空闲的互斥锁，则无死锁

### 信号量死锁检测
使用**银行家算法**：
1. 若信号量可用计数 > 0，不会阻塞 → 安全
2. 否则，为所有线程构建分配/需求矩阵
3. 运行迭代安全性检查：找到需求可被当前工作向量满足的线程，释放其分配的资源，重复此过程
4. 若所有线程都能完成 → 安全；若陷入僵局 → 死锁 → 返回 `-0xDEAD`

### 影子状态跟踪
由于 tg-sync 的内部状态不可查询，内核在 `Process` 中维护影子跟踪：
- `mutex_holder[mutex_id]`：每个互斥锁的持有线程
- `mutex_wait[tid]`：每个阻塞线程正在等待的互斥锁
- `sem_available[sem_id]`：每个信号量的当前可用计数
- `sem_alloc[sem_id][tid]`：每个线程持有的每个信号量的资源数
- `sem_wait[tid]`：每个阻塞线程正在等待的信号量

所有跟踪在 create/lock/unlock/up/down 操作以及阻塞线程被唤醒时更新。

## 遇到的问题

1. **创建时跟踪状态未初始化**：最初忘记在创建新信号量时扩展 `sem_available` 和 `sem_alloc` 向量，导致索引越界 panic。修复方法：确保在 `semaphore_create` 和 `mutex_create` 中将向量扩展到与信号量/互斥锁列表大小匹配。

2. **被唤醒线程的分配未更新**：当 `semaphore_up` 唤醒一个阻塞线程时，该线程成功获取了信号量。最初忘记递增被唤醒线程的分配计数和清除其 `sem_wait` 条目，导致银行家算法使用过期数据。修复方法：在 `semaphore_up` 和 `mutex_unlock` 中更新被唤醒线程的跟踪状态。

3. **设计复杂度**：最初的方案尝试将 `[u32; 500]` 系统调用计数器直接放入 Process 结构体（从第三/四章的经验中吸取教训）。第八章从一开始就选用 `BTreeMap` 和 `Vec` 进行跟踪，避免了结构体膨胀问题。同时为互斥锁选择了等待图（比完整银行家算法更简单），为信号量选择了银行家算法（由于计数 > 1 的语义，这是必要的）。

## 后续修复

- **`condvar_wait` 未更新互斥锁跟踪状态**：`condvar_wait` 内部会释放互斥锁并阻塞当前线程，但最初未更新 `mutex_holder` 和 `mutex_wait` 跟踪状态。这会导致死锁检测算法在涉及条件变量+互斥锁交互时使用过期数据（例如，一个已被 condvar 释放的互斥锁在跟踪中仍显示被持有）。修复方法：在调用 `wait_with_mutex` 之前清除 `mutex_holder[mutex_id]`；当唤醒的线程从互斥锁等待队列中出队时，更新其为新的持有者并清除其 `mutex_wait` 条目。
